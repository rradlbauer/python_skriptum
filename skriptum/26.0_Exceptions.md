# 1. Warum brauchen wir Exceptions?

In Programmen können Situationen auftreten, in denen eine normale Berechnung nicht sinnvoll fortgesetzt werden kann.

Beispiele:

```text
Eine Zahl soll durch 0 dividiert werden.

Ein Datum liegt in der Zukunft, obwohl ein vergangenes Datum erwartet wird.

Eine Datei existiert nicht.

Ein Text soll in eine Zahl umgewandelt werden, enthält aber Buchstaben.

Von einem Konto soll mehr Geld abgehoben werden, als verfügbar ist.
```

Python kann viele solcher Fehler selbst erkennen.

Beispiel:

```python
zahl = int("Hallo")
```

Dabei entsteht eine Exception:

```text
ValueError
```

Auch eigener Code kann feststellen:

```text
Diese Operation ist unter den gegebenen Bedingungen nicht sinnvoll.
```

Dann kann der Code selbst eine Exception auslösen.

---

# 2. Was ist eine Exception?

Eine **Exception** ist ein Objekt, das eine außergewöhnliche Fehler- oder Ausnahmesituation beschreibt.

Beispiel:

```python
ValueError("Ungültiger Wert")
```

Das ist ein Exception-Objekt der Klasse `ValueError`.

Mit:

```python
raise ValueError("Ungültiger Wert")
```

wird diese Exception ausgelöst.

Der normale Ablauf wird an dieser Stelle unterbrochen.

---

# 3. Eine Fehlermeldung ausgeben reicht oft nicht

Angenommen, wir schreiben eine Funktion zur Altersberechnung.

Eine naive Variante könnte so aussehen:

```python
from datetime import date


def berechne_alter(geburtsdatum: date) -> int:
    heute = date.today()

    if geburtsdatum > heute:
        print("Geburtsdatum liegt in der Zukunft!")

    alter = heute.year - geburtsdatum.year

    if (heute.month, heute.day) < (
        geburtsdatum.month,
        geburtsdatum.day
    ):
        alter -= 1

    return alter
```

Das Problem:

> Die Funktion meldet zwar einen Fehler, berechnet aber trotzdem weiter.

Der Aufrufer erhält möglicherweise einen ungültigen Rückgabewert.

---

# 4. Warum `// 365` für Alter ungenau ist

Eine häufige vereinfachte Berechnung lautet:

```python
alter = (heute - geburtsdatum).days // 365
```

Das ist für ein exaktes Alter in Jahren nicht zuverlässig.

Gründe:

- Jahre haben nicht immer 365 Tage.
- Schaltjahre besitzen 366 Tage.

Besser ist:

```python
alter = heute.year - geburtsdatum.year

if (heute.month, heute.day) < (
    geburtsdatum.month,
    geburtsdatum.day
):
    alter -= 1
```

Damit wird geprüft, ob der Geburtstag im aktuellen Jahr bereits stattgefunden hat.

---

# 5. Einen Fehler mit `raise` signalisieren

Eine bessere Funktion lautet:

```python
from datetime import date


def berechne_alter(geburtsdatum: date) -> int:
    heute = date.today()

    if geburtsdatum > heute:
        raise ValueError(
            "Geburtsdatum liegt in der Zukunft."
        )

    alter = heute.year - geburtsdatum.year

    if (heute.month, heute.day) < (
        geburtsdatum.month,
        geburtsdatum.day
    ):
        alter -= 1

    return alter
```

Mit:

```python
raise ValueError(...)
```

wird die normale Ausführung sofort beendet.

Die Funktion liefert in diesem Fehlerfall **keinen normalen Rückgabewert**.

---

# 6. Was passiert bei `raise`?

Betrachte:

```python
def pruefe_alter(alter: int) -> None:
    if alter < 0:
        raise ValueError("Alter darf nicht negativ sein.")

    print("Alter ist gültig.")
```

Bei:

```python
pruefe_alter(-5)
```

passiert:

```text
1. alter < 0 ist True.

2. ValueError wird erzeugt.

3. raise löst die Exception aus.

4. Die Funktion wird sofort verlassen.

5. Nachfolgender Code in der Funktion wird nicht mehr ausgeführt.

6. Python sucht beim Aufrufer nach einem passenden except-Block.
```

---

# 7. Eine Exception ist kein normaler Rückgabewert

Diese beiden Konzepte dürfen nicht verwechselt werden.

## Normaler Rückgabewert

```python
def quadrat(x: int) -> int:
    return x * x
```

Der Aufrufer bekommt einen Wert zurück.

## Exception

```python
def wurzel_vorbereiten(x: float) -> float:
    if x < 0:
        raise ValueError("x darf nicht negativ sein.")

    return x
```

Im Fehlerfall gibt es keinen normalen Rückgabewert.

Stattdessen ändert sich der Kontrollfluss.

---

# 8. Warum Exceptions besser als spezielle Fehlerwerte sein können

Man könnte Fehler auch durch spezielle Rückgabewerte melden:

```text
def suche_name(...) -> str | None:
    ...
```

Das ist sinnvoll, wenn `None` ein normal erwartbarer Fall ist.

Zum Beispiel:

```text
Name wurde nicht gefunden.
```

Eine Exception ist eher geeignet, wenn eine Operation **nicht sinnvoll durchgeführt werden kann**.

Beispiel:

```text
Ungültiges Geburtsdatum.

Ungültiges Zahlenformat.

Datei konnte nicht geöffnet werden.
```

Faustregel:

```text
normal erwartbarer Sonderfall
→ oft Rückgabewert wie None sinnvoll

fehlerhafte oder nicht erfüllbare Operation
→ Exception kann sinnvoll sein
```

---

# 9. Exceptions behandeln: `try` und `except`

Eine Exception muss nicht zum Abbruch des gesamten Programms führen.

Sie kann behandelt werden:

```python
from datetime import date


try:
    alter = berechne_alter(
        date(2099, 1, 1)
    )

    print(f"Alter: {alter}")

except ValueError as e:
    print(f"Fehler: {e}")
```

Da das Datum in der Zukunft liegt, wird `ValueError` ausgelöst.

Python springt zum passenden `except`-Block.

---

# 10. Ablauf eines `try`-Blocks

Vereinfacht:

```text
try:
    Code A
    Code B
    Code C

except ValueError:
    Fehlerbehandlung
```

Wenn bei `Code B` eine passende Exception entsteht:

```text
Code A
→ wird ausgeführt

Code B
→ Exception

Code C
→ wird übersprungen

except
→ wird ausgeführt
```

Die Ausführung wird also nicht nach der fehlerhaften Zeile im `try`-Block fortgesetzt.

---

# 11. Das Exception-Objekt mit `as`

```text
except ValueError as e:
    print(e)
```

Die Variable `e` verweist auf das ausgelöste Exception-Objekt.

Beispiel:

```python
try:
    int("abc")

except ValueError as e:
    print(type(e))
    print(e)
```

Die genaue Meldung stammt aus dem Exception-Objekt.

---

# 12. Möglichst spezifische Exceptions behandeln

Man könnte schreiben:

```python
try:
    ...
except Exception as e:
    print(e)
```

Das fängt sehr viele unterschiedliche Fehlerarten ab.

Für kleine Demonstrationen kann das nützlich sein.

In produktivem Code ist es aber oft besser, möglichst gezielt zu behandeln:

```python
try:
    zahl = int(eingabe)

except ValueError:
    print("Bitte eine gültige Ganzzahl eingeben.")
```

Warum?

> Wenn man zu breit fängt, kann man versehentlich auch Programmierfehler verstecken, die man eigentlich sehen und beheben sollte.

---

# 13. Mehrere `except`-Blöcke

Unterschiedliche Fehler können unterschiedlich behandelt werden.

```python
try:
    datei = open("daten.txt", "r", encoding="utf-8")
    zahl = int(datei.readline())

except FileNotFoundError:
    print("Die Datei wurde nicht gefunden.")

except ValueError:
    print("Die Datei enthält keine gültige Ganzzahl.")
```

Python verwendet den ersten passenden `except`-Block.

---

# 14. Mehrere Exception-Typen gemeinsam behandeln

Wenn mehrere Fehler gleich behandelt werden sollen:

```python
try:
    ...
except (ValueError, TypeError) as e:
    print(f"Ungültige Daten: {e}")
```

Die Exception-Typen stehen dabei in einem Tupel.

---

# 15. Die Exception-Hierarchie

Exception-Klassen stehen selbst in einer Vererbungshierarchie.

Vereinfacht:

```text
BaseException
│
├── SystemExit
├── KeyboardInterrupt
└── Exception
    │
    ├── ValueError
    ├── TypeError
    ├── LookupError
    │   ├── IndexError
    │   └── KeyError
    ├── OSError
    │   └── FileNotFoundError
    └── ...
```

Für normalen Anwendungscode werden üblicherweise Exceptions behandelt, die von:

```python
Exception
```

erben.

---

# 16. Warum `except Exception` nicht wirklich alles fängt

Die Aussage:

```text
Exception fängt alle Exceptions.
```

ist technisch nicht ganz korrekt.

Einige spezielle Ausnahmen wie:

```text
KeyboardInterrupt
SystemExit
```

erben direkt von `BaseException`, nicht von `Exception`.

Das ist sinnvoll, weil ein Programm beispielsweise einen Benutzerabbruch mit `Ctrl+C` nicht versehentlich immer verschlucken sollte.

Für normalen Anwendungscode gilt daher:

> Wenn breit gefangen werden muss, verwende eher `Exception` als `BaseException`.

---

# 17. Reihenfolge der `except`-Blöcke

Spezifische Exception-Typen müssen vor allgemeineren stehen.

Sinnvoll:

```python
try:
    ...
except FileNotFoundError:
    ...
except OSError:
    ...
except Exception:
    ...
```

`FileNotFoundError` ist eine Unterklasse von `OSError`.

Würde zuerst `OSError` stehen, würde der speziellere Block danach nicht mehr erreicht.

---

# 18. `else`: Code nur bei erfolgreichem `try`

Ein `try`-Block kann einen `else`-Teil besitzen.

```python
try:
    zahl = int("42")

except ValueError:
    print("Ungültige Zahl.")

else:
    print(f"Erfolgreich gelesen: {zahl}")
```

Der `else`-Block wird nur ausgeführt, wenn im `try`-Block keine Exception auftritt.

---

# 19. Warum `else` nützlich ist

Ungünstig:

```python
try:
    zahl = int(eingabe)
    verarbeite(zahl)

except ValueError:
    ...
```

Falls auch `verarbeite()` einen `ValueError` erzeugt, würde dieser möglicherweise versehentlich als Eingabefehler behandelt.

Besser:

```python
try:
    zahl = int(eingabe)

except ValueError:
    print("Ungültige Zahl.")

else:
    verarbeite(zahl)
```

Damit ist klar:

> Der `except`-Block behandelt nur Fehler aus dem Teil, den wir tatsächlich absichern wollten.

---

# 20. `finally`: Code, der immer ausgeführt wird

Ein `finally`-Block wird unabhängig davon ausgeführt, ob eine Exception entstanden ist.

```python
try:
    print("try")

finally:
    print("finally")
```

Auch bei einer Exception wird `finally` ausgeführt, bevor die Exception weitergegeben wird.

---

# 21. Typischer Aufbau

```python
try:
    ...
except ValueError:
    ...
else:
    ...
finally:
    ...
```

Bedeutung:

```text
try
→ riskanter Code

except
→ Fehler behandeln

else
→ nur bei erfolgreichem try

finally
→ immer ausführen
```

Nicht jeder Block muss vorhanden sein.

---

# 22. Beispiel: Konto

Wir definieren ein Konto:

```python
class Konto:
    def __init__(self, saldo: float = 0.0) -> None:
        if saldo < 0:
            raise ValueError(
                "Startsaldo darf nicht negativ sein."
            )

        self.saldo: float = saldo

    def abheben(self, betrag: float) -> None:
        if betrag <= 0:
            raise ValueError(
                "Betrag muss positiv sein."
            )

        if betrag > self.saldo:
            raise ValueError(
                "Nicht genügend Guthaben."
            )

        self.saldo -= betrag

    def einzahlen(self, betrag: float) -> None:
        if betrag <= 0:
            raise ValueError(
                "Betrag muss positiv sein."
            )

        self.saldo += betrag
```

Hier schützt die Klasse ihren gültigen Zustand.

---

# 23. Warum die Prüfung in der Klasse sinnvoll ist

Ohne Prüfung könnte jemand schreiben:

```python
konto.einzahlen(-500)
```

Dann würde eine Einzahlung den Kontostand verringern.

Oder:

```python
konto.abheben(-500)
```

könnte den Kontostand erhöhen.

Die Methoden sollten daher Regeln durchsetzen.

Wenn eine Operation gegen diese Regeln verstößt:

```python
raise ValueError(...)
```

---

# 24. Eine Überweisung

Eine einfache Funktion:

```python
def ueberweisen(
    von: Konto,
    nach: Konto,
    betrag: float
) -> None:
    von.abheben(betrag)
    nach.einzahlen(betrag)
```

Hier ist die Reihenfolge bewusst gewählt:

```text
1. zuerst prüfen und abbuchen
2. danach einzahlen
```

Da `abheben()` bei unzureichendem Guthaben eine Exception auslöst, wird das Zielkonto in diesem Fall gar nicht verändert.

---

# 25. Konsistenter Zustand

Ein Programm sollte auch bei Fehlern möglichst einen gültigen Zustand behalten.

Problematisch wäre:

```python
def ueberweisen(
    von: Konto,
    nach: Konto,
    betrag: float
) -> None:
    nach.einzahlen(betrag)
    von.abheben(betrag)
```

Wenn `von.abheben()` scheitert, wurde das Zielkonto bereits erhöht.

Dann gilt:

```text
Überweisung fehlgeschlagen

aber Zielkonto hat trotzdem Geld erhalten
```

Das ist ein inkonsistenter Zustand.

---

# 26. Fehler möglichst vermeiden, bevor Zustand verändert wird

Die einfachste Lösung ist oft:

> Prüfe Bedingungen, bevor du irreversible oder schwer rückgängig zu machende Änderungen durchführst.

Darum ist:

```python
von.abheben(betrag)
nach.einzahlen(betrag)
```

besser als die umgekehrte Reihenfolge.

In echten Systemen wie Datenbanken gibt es dafür Transaktionen.

---

# 27. Wenn eine Änderung rückgängig gemacht werden muss

Manchmal lässt sich eine Reihenfolge nicht ändern oder mehrere Schritte können nacheinander fehlschlagen.

Dann kann eine Rücksetzstrategie notwendig sein.

Vereinfachtes Beispiel:

```python
def ueberweisen_unsicher(
    von: Konto,
    nach: Konto,
    betrag: float
) -> None:
    nach.einzahlen(betrag)

    try:
        von.abheben(betrag)

    except ValueError:
        nach.abheben(betrag)
        raise
```

Wenn das Abbuchen fehlschlägt:

```text
1. Zielkonto wurde bereits erhöht.
2. Einzahlung wird rückgängig gemacht.
3. Die ursprüngliche Exception wird weitergegeben.
```

---

# 28. Warum hier `raise` und nicht `raise e`?

Innerhalb eines `except`-Blocks kann die aktuell behandelte Exception einfach erneut ausgelöst werden:

```python
raise
```

Das ist beim unveränderten Weiterwerfen normalerweise die beste Form.

```text
except ValueError:
    ...
    raise
```

Dadurch bleibt der ursprüngliche Zusammenhang des Tracebacks erhalten.

Dagegen:

```python
raise e
```

wirft zwar ebenfalls die Exception weiter, verändert aber die sichtbare Traceback-Struktur und ist für reines Weiterreichen meist nicht die gewünschte Variante.

Merke:

```text
dieselbe Exception unverändert weitergeben
→ raise
```

---

# 29. Exceptions können mehrere Ebenen nach oben wandern

Betrachte:

```text
main()
  │
  ▼
ueberweisen()
  │
  ▼
abheben()
  │
  ▼
ValueError
```

Wenn `abheben()` die Exception nicht behandelt, gelangt sie zu `ueberweisen()`.

Wenn auch `ueberweisen()` sie nicht behandelt, gelangt sie weiter zum Aufrufer.

Python sucht also entlang der Aufrufkette nach einem passenden `except`.

Diesen Vorgang nennt man oft **Exception Propagation**.

---

# 30. Eine Exception behandeln oder weitergeben?

Nicht jede Funktion sollte jede Exception selbst behandeln.

Beispiel:

```text
def abheben(...) -> None:
    ...
```

Die Methode weiß:

```text
Die Operation ist ungültig.
```

Sie weiß aber möglicherweise nicht:

```text
Soll eine GUI eine Meldung anzeigen?

Soll ein Webserver HTTP 400 senden?

Soll ein Log geschrieben werden?

Soll der Benutzer erneut gefragt werden?
```

Deshalb ist eine gute Aufgabenteilung oft:

```text
tiefe Ebene
→ Fehler erkennen und Exception auslösen

höhere Ebene
→ entscheiden, wie der Fehler dem Benutzer präsentiert wird
```

---

# 31. Exception nicht zu früh in Text umwandeln

Ungünstig:

```text
def abheben(...) -> None:
    try:
        ...
    except ValueError as e:
        print(f"Fehler: {e}")
```

Damit entscheidet eine fachliche Klasse selbst über die Benutzeroberfläche.

Besser:

```text
def abheben(...) -> None:
    if ...:
        raise ValueError(...)
```

Und weiter oben:

```python
try:
    konto.abheben(100)

except ValueError as e:
    print(f"Fehler: {e}")
```

So bleibt die Fachlogik unabhängig von der Darstellung.

# 32. Eigene Exception-Klassen

Manchmal ist `ValueError` zu allgemein.

Für unser Konto könnten wir eigene Exceptions definieren:

```python
class KontoFehler(Exception):
    pass


class NichtGenugGuthaben(KontoFehler):
    pass


class UngueltigerBetrag(KontoFehler):
    pass
```

Dann:

```python
class Konto:
    def __init__(self, saldo: float = 0.0) -> None:
        self.saldo: float = saldo

    def abheben(self, betrag: float) -> None:
        if betrag <= 0:
            raise UngueltigerBetrag(
                "Betrag muss positiv sein."
            )

        if betrag > self.saldo:
            raise NichtGenugGuthaben(
                "Nicht genügend Guthaben."
            )

        self.saldo -= betrag
```

---

# 33. Warum eigene Exceptions?

Der Aufrufer kann nun gezielt reagieren:

```python
try:
    konto.abheben(150)

except NichtGenugGuthaben:
    print("Bitte einen kleineren Betrag wählen.")

except UngueltigerBetrag:
    print("Der Betrag muss größer als 0 sein.")
```

Das ist aussagekräftiger als alle fachlichen Probleme als allgemeinen `ValueError` zu behandeln.

---

# 34. Gemeinsame Basisklasse für eigene Exceptions

Durch:

```python
class KontoFehler(Exception):
    pass
```

können alle Konto-Fehler auch gemeinsam behandelt werden:

```python
try:
    ...

except KontoFehler as e:
    print(f"Kontofehler: {e}")
```

Damit nutzen wir direkt die Vererbung aus Kapitel 25.

---

# 35. Exceptions sind ebenfalls Objekte und Klassen

Auch hier gilt das bekannte objektorientierte Modell.

```python
e = ValueError("Ungültiger Wert")
```

`e` verweist auf ein Objekt der Klasse `ValueError`.

Und:

```python
ValueError
```

ist selbst eine Klasse.

Die Exception-Hierarchie funktioniert durch Vererbung.

Das verbindet Exceptions direkt mit den vorherigen Kapiteln zu:

```text
Klassen
Vererbung
Polymorphie
```

# 36. Eine Exception in eine passendere Exception übersetzen

Angenommen, eine Funktion liest ein Geburtsdatum aus Text:

```python
from datetime import datetime


def parse_geburtsdatum(text: str) -> date:
    return datetime.strptime(
        text,
        "%d.%m.%Y"
    ).date()
```

`strptime()` löst bei ungültigem Format einen `ValueError` aus.

Vielleicht möchten wir eine fachlich klarere Exception weitergeben.

---

# 37. Exception Chaining mit `raise ... from ...`

```python
class UngueltigesGeburtsdatum(Exception):
    pass


def parse_geburtsdatum(text: str) -> date:
    try:
        return datetime.strptime(
            text,
            "%d.%m.%Y"
        ).date()

    except ValueError as e:
        raise UngueltigesGeburtsdatum(
            f"Ungültiges Geburtsdatum: {text}"
        ) from e
```

Das:

```text
from e
```

erhält die ursprüngliche Exception als Ursache.

Der Traceback kann dadurch zeigen:

```text
ursprünglicher ValueError
→ führte zu
UngueltigesGeburtsdatum
```

---

# 38. Warum Exception Chaining nützlich ist

Ohne Kontext sieht man vielleicht nur:

```text
Ungültiges Geburtsdatum.
```

Mit Chaining kann beim Debuggen zusätzlich sichtbar bleiben:

```text
Warum genau konnte das Datum nicht gelesen werden?
```

Das ist besonders in größeren Programmen hilfreich.

# 39. Ressourcen und `finally`

Manche Ressourcen müssen nach der Verwendung freigegeben werden.

Beispiele:

```text
Dateien
Netzwerkverbindungen
Datenbankverbindungen
Locks
```

Eine klassische Lösung verwendet `finally`.

```python
datei = None

try:
    datei = open(
        "kontostaende.txt",
        "r",
        encoding="utf-8"
    )

    inhalt = datei.read()

finally:
    if datei is not None:
        datei.close()
```

Der `finally`-Block wird unabhängig vom Erfolg ausgeführt.

---

# 40. Problem im ursprünglichen `finally`-Muster

Folgender Code ist riskant:

```python
try:
    datei = open("daten.txt", "r")

finally:
    datei.close()
```

Wenn bereits `open()` fehlschlägt, wurde `datei` möglicherweise noch gar nicht gebunden.

Dann kann im `finally`-Block ein weiterer Fehler entstehen.

Deshalb müsste man bei manueller Verwaltung sorgfältiger arbeiten.

Noch besser ist für Dateien meistens:

> Verwende `with`.

---

# 41. Ressourcen sicher mit `with` verwalten

```python
with open(
    "kontostaende.txt",
    "r",
    encoding="utf-8"
) as datei:
    inhalt = datei.read()
```

Nach Verlassen des `with`-Blocks wird die Datei automatisch geschlossen.

Das gilt auch dann, wenn innerhalb des Blocks eine Exception auftritt.

---

# 42. Warum `with` für Dateien meist besser als `finally` ist

Vergleich:

## Manuell

```python
datei = open(...)

try:
    ...
finally:
    datei.close()
```

## Mit Context Manager

```python
with open(...) as datei:
    ...
```

Die zweite Variante ist:

- kürzer,
- klarer,
- weniger fehleranfällig.

Für Dateien sollte daher normalerweise `with` bevorzugt werden.

---

# 43. `with` und Exceptions kombinieren

```python
try:
    with open(
        "kontostaende.txt",
        "r",
        encoding="utf-8"
    ) as datei:
        konto1 = Konto(
            float(datei.readline())
        )

        konto2 = Konto(
            float(datei.readline())
        )

except FileNotFoundError:
    print("Datei wurde nicht gefunden.")

except ValueError as e:
    print(f"Ungültige Daten: {e}")
```

Die Datei wird automatisch geschlossen.

Die Fehlerbehandlung bleibt getrennt.

---

# 44. `finally` bleibt trotzdem wichtig

`with` ersetzt nicht jeden Einsatz von `finally`.

`finally` ist allgemein nützlich, wenn etwas garantiert ausgeführt werden muss.

Beispiel:

```python
def verarbeite() -> None:
    print("Start")

    try:
        riskante_operation()

    finally:
        print("Aufräumen")
```

Auch wenn `riskante_operation()` scheitert, wird `"Aufräumen"` ausgegeben.

---

# 45. `return` und `finally`

Auch wenn ein `return` im `try` vorkommt, wird der `finally`-Block vorher ausgeführt.

```python
def beispiel() -> int:
    try:
        return 42

    finally:
        print("finally")
```

Beim Aufruf wird zuerst ausgegeben:

```text
finally
```

Danach wird `42` zurückgegeben.

---

# 46. Vorsicht mit `return` im `finally`

Ein `return` innerhalb von `finally` ist fast immer problematisch.

Es kann einen normalen Rückgabewert oder sogar eine Exception verdecken.

Deshalb:

> Verwende `finally` hauptsächlich zum Aufräumen, nicht zur Steuerung des normalen Rückgabewerts.

---

# 47. `try`-Blöcke klein halten

Ungünstig:

```python
try:
    datei_lesen()
    daten_umwandeln()
    berechnen()
    speichern()
    statistik_erstellen()

except ValueError:
    print("Fehler")
```

Es ist schwer zu erkennen, welcher Teil den Fehler verursacht hat und ob der `except`-Block wirklich dafür gedacht ist.

Besser:

> Umgib nur den Code mit `try`, dessen Exception du an dieser Stelle tatsächlich behandeln möchtest.

---

# 48. Exceptions nicht als normale Schleifensteuerung missbrauchen

Exceptions sind für außergewöhnliche Situationen gedacht.

Ungünstig:

```python
for zahl in zahlen:
    try:
        if zahl % 2 == 0:
            raise Exception()

    except Exception:
        print("gerade")
```

Viel klarer:

```python
for zahl in zahlen:
    if zahl % 2 == 0:
        print("gerade")
```

Exceptions sollten normale Bedingungen nicht unnötig ersetzen.

---

# 49. Eingaben behandeln

Ein klassischer Anwendungsfall:

```python
eingabe = input("Alter: ")

try:
    alter = int(eingabe)

except ValueError:
    print("Bitte eine gültige Ganzzahl eingeben.")

else:
    print(f"Alter: {alter}")
```

Hier wird eine erwartbare fehlerhafte Benutzereingabe abgefangen.

---

# 50. Mehrfach versuchen

Manchmal soll der Benutzer bei einer ungültigen Eingabe erneut gefragt werden.

```python
while True:
    eingabe = input("Ganzzahl: ")

    try:
        zahl = int(eingabe)

    except ValueError:
        print("Ungültige Eingabe.")

    else:
        break

print(f"Eingegeben: {zahl}")
```

Die Exception wird dort behandelt, wo sinnvoll reagiert werden kann.

---

# 51. Nicht jede Exception muss behandelt werden

Während der Entwicklung ist es oft hilfreich, unerwartete Exceptions **nicht** sofort abzufangen.

Warum?

Dann zeigt Python einen Traceback.

Dieser enthält wichtige Informationen zum Debuggen:

```text
Exception-Typ
Fehlermeldung
Aufrufkette
Datei und Zeilennummern
```

Wenn man jede Exception sofort mit:

```text
except Exception:
    print("Fehler")
```

versteckt, verliert man wertvolle Informationen.

---

# 52. Was ist ein Traceback?

Ein Traceback zeigt, wie Python zur fehlerhaften Stelle gelangt ist.

Vereinfacht:

```text
main()
  ↓
funktion_a()
  ↓
funktion_b()
  ↓
ValueError
```

Damit lässt sich nachvollziehen:

```text
Wo wurde die Exception ausgelöst?

Welche Funktionen wurden davor aufgerufen?
```

Das ist eines der wichtigsten Debugging-Werkzeuge in Python.

---

# 53. Fehlermeldung für Benutzer vs. Diagnose für Entwickler

Benutzer benötigen oft eine verständliche Meldung:

```text
Bitte geben Sie ein gültiges Datum ein.
```

Entwickler benötigen möglicherweise zusätzlich:

```text
Traceback
Exception-Typ
technische Ursache
```

Diese beiden Ziele sollten nicht verwechselt werden.

Ein gutes Programm kann Benutzern klare Meldungen zeigen und technische Informationen zusätzlich protokollieren.

---

# 54. Eine Exception sollte aussagekräftig sein

Wenig hilfreich:

```python
raise ValueError("Fehler")
```

Besser:

```python
raise ValueError(
    "Geburtsdatum darf nicht in der Zukunft liegen."
)
```

Oder:

```python
raise ValueError(
    f"Betrag muss positiv sein, erhalten: {betrag}"
)
```

Die Meldung sollte erklären:

```text
Was ist falsch?

Welche Bedingung wurde verletzt?
```

---

# 55. Welcher eingebaute Exception-Typ passt?

Einige häufige Typen:

| Exception | Typischer Einsatz |
|---|---|
| `ValueError` | richtiger Datentyp, aber ungültiger Wert |
| `TypeError` | Objekt hat einen ungeeigneten Typ |
| `IndexError` | ungültiger Listen-/Sequenzindex |
| `KeyError` | Schlüssel fehlt in einem Dictionary |
| `FileNotFoundError` | Datei wurde nicht gefunden |
| `ZeroDivisionError` | Division durch 0 |
| `AttributeError` | Objekt besitzt erwartetes Attribut nicht |
| `RuntimeError` | allgemeiner Laufzeitfehler, wenn nichts Spezifischeres passt |

Oft werden diese Exceptions bereits von Python selbst ausgelöst.

---

# 56. `ValueError` oder `TypeError`?

Beispiel:

```python
def setze_prozent(prozent: float) -> None:
    if prozent < 0 or prozent > 100:
        raise ValueError(
            "Prozent muss zwischen 0 und 100 liegen."
        )
```

Der Typ kann korrekt sein:

```text
float
```

aber der Wert ist ungültig.

→ `ValueError`

Wenn eine Funktion ausdrücklich zur Laufzeit einen falschen Typ prüfen muss, kann `TypeError` passend sein.

In normal typisiertem Anwendungscode werden viele Typfehler aber bereits durch Type Checker oder durch Operationen selbst sichtbar.

---

# 57. Vollständiges Beispiel: sichere Überweisung

Wir verbinden mehrere Konzepte.

```python
class KontoFehler(Exception):
    pass


class UngueltigerBetrag(KontoFehler):
    pass


class NichtGenugGuthaben(KontoFehler):
    pass


class Konto:
    def __init__(self, saldo: float = 0.0) -> None:
        if saldo < 0:
            raise ValueError(
                "Startsaldo darf nicht negativ sein."
            )

        self.saldo: float = saldo

    def einzahlen(self, betrag: float) -> None:
        if betrag <= 0:
            raise UngueltigerBetrag(
                "Einzahlungsbetrag muss positiv sein."
            )

        self.saldo += betrag

    def abheben(self, betrag: float) -> None:
        if betrag <= 0:
            raise UngueltigerBetrag(
                "Abhebungsbetrag muss positiv sein."
            )

        if betrag > self.saldo:
            raise NichtGenugGuthaben(
                "Nicht genügend Guthaben."
            )

        self.saldo -= betrag


def ueberweisen(
    von: Konto,
    nach: Konto,
    betrag: float
) -> None:
    von.abheben(betrag)

    try:
        nach.einzahlen(betrag)

    except Exception:
        von.einzahlen(betrag)
        raise
```

---

# 58. Warum gibt es hier trotzdem einen Rollback?

Wir buchen zuerst vom Quellkonto ab.

Das schützt vor dem ursprünglichen Problem:

```text
unzureichendes Guthaben
```

Aber auch `nach.einzahlen()` könnte theoretisch scheitern.

Dann wäre das Geld bereits vom Quellkonto abgebucht.

Deshalb wird in diesem Fehlerfall zurückgebucht:

```python
von.einzahlen(betrag)
```

Danach:

```python
raise
```

Damit wird die ursprüngliche Exception weitergegeben.

---

# 59. Grenzen des vereinfachten Rollbacks

Dieses Beispiel zeigt nur das Konzept.

In echten Finanzsystemen reicht solch einfacher Anwendungscode nicht aus.

Dort benötigt man unter anderem:

```text
echte Datenbanktransaktionen
Nebenläufigkeitskontrolle
dauerhafte Speicherung
Protokollierung
atomare Operationen
```

Der wichtige Gedanke für dieses Kapitel lautet:

> Fehlerbehandlung muss auch den Zustand des Programms berücksichtigen.

# 60. Typische Fehler und Missverständnisse

## Nur `print()` verwenden, obwohl die Operation ungültig ist

```python
if fehler:
    print("Fehler")
```

und danach trotzdem weiterrechnen ist oft problematisch.

---

## Jede Exception mit `Exception` fangen

```text
except Exception:
    ...
```

kann unerwartete Programmierfehler verstecken.

Behandle möglichst spezifisch.

---

## Leeren `except` verwenden

Sehr problematisch:

```python
try:
    ...
except:
    pass
```

Dadurch verschwinden Fehler vollständig.

---

## Exception fangen und nichts tun

```text
except ValueError:
    pass
```

kann sinnvoll sein, ist aber selten.

Wenn ein Fehler bewusst ignoriert wird, sollte das gut begründet sein.

---

## `raise e` zum bloßen Weiterwerfen verwenden

Besser:

```text
except ValueError:
    ...
    raise
```

wenn dieselbe Exception weitergegeben werden soll.

---

## Zu großen `try`-Block verwenden

Nur Code, dessen Exception an dieser Stelle sinnvoll behandelt werden kann, sollte im `try` liegen.

---

## Ressourcen manuell schließen, obwohl `with` verfügbar ist

Für Dateien:

```python
with open(...) as datei:
    ...
```

ist normalerweise klarer und sicherer.

---

## Exception Handling mit Fehlervermeidung verwechseln

Exceptions ersetzen keine guten Vorbedingungen und sinnvolle Reihenfolge von Operationen.

## Übung 1 – Eingabe sicher verarbeiten

Schreibe eine Funktion:

```python
def lese_prozent(text: str) -> float:
    ...
```

Regeln:

- `text` soll in `float` umgewandelt werden.
- Werte kleiner als `0` oder größer als `100` sind ungültig.
- Bei ungültigem Zahlenformat soll eine verständliche eigene Fehlermeldung entstehen.
- Bei einem Wert außerhalb des Bereichs ebenfalls.
- Der Aufrufer soll beide Fehler als `ValueError` behandeln können.

### Lösungsschema

Es gibt zwei Fehlerquellen:

```text
1. float(text)
   → kann ValueError auslösen

2. Bereich
   → 0 <= wert <= 100
```

Für den ersten Fehler kann die bestehende Exception abgefangen und mit einer klareren Meldung weitergegeben werden.

Mögliche Struktur:

```text
try:
    umwandeln
except ValueError as e:
    neue ValueError mit from e

danach:
    Bereich prüfen

wenn ungültig:
    ValueError
```

<details>
<summary>Vollständige Lösung anzeigen</summary>

```python
def lese_prozent(text: str) -> float:
    try:
        wert = float(text)

    except ValueError as e:
        raise ValueError(
            f"'{text}' ist keine gültige Zahl."
        ) from e

    if wert < 0 or wert > 100:
        raise ValueError(
            "Prozentwert muss zwischen 0 und 100 liegen."
        )

    return wert
```

Verwendung:

```python
try:
    prozent = lese_prozent("125")
    print(prozent)

except ValueError as e:
    print(f"Fehler: {e}")
```

</details>

## Übung 2 – Eigene Exception-Klasse

Modelliere eine Klasse `Lager`.

Sie besitzt:

```text
bestand: int
```

Die Methode:

```text
entnehmen(anzahl: int)
```

soll:

- bei `anzahl <= 0` einen `ValueError` auslösen,
- bei zu geringem Bestand eine eigene Exception `NichtGenugBestand` auslösen,
- sonst den Bestand verringern.

### Lösungsschema

Zuerst eigene Exception:

```text
NichtGenugBestand
→ erbt von Exception
```

Dann Reihenfolge der Prüfungen:

```text
1. anzahl <= 0
   → ValueError

2. anzahl > bestand
   → NichtGenugBestand

3. sonst Bestand ändern
```

<details>
<summary>Vollständige Lösung anzeigen</summary>

```python
class NichtGenugBestand(Exception):
    pass


class Lager:
    def __init__(self, bestand: int) -> None:
        if bestand < 0:
            raise ValueError(
                "Bestand darf nicht negativ sein."
            )

        self.bestand: int = bestand

    def entnehmen(self, anzahl: int) -> None:
        if anzahl <= 0:
            raise ValueError(
                "Anzahl muss positiv sein."
            )

        if anzahl > self.bestand:
            raise NichtGenugBestand(
                "Nicht genügend Bestand vorhanden."
            )

        self.bestand -= anzahl
```

Verwendung:

```python
lager = Lager(10)

try:
    lager.entnehmen(15)

except NichtGenugBestand as e:
    print(f"Lagerfehler: {e}")

except ValueError as e:
    print(f"Ungültiger Wert: {e}")
```

</details>

## Übung 3 – Datei lesen mit `with`

Eine Datei `werte.txt` enthält in jeder Zeile eine Zahl.

Schreibe eine Funktion:

```python
def lese_werte(dateiname: str) -> list[float]:
    ...
```

Sie soll:

- die Datei mit `with` öffnen,
- jede Zeile in `float` umwandeln,
- bei einer fehlenden Datei `FileNotFoundError` weitergeben,
- bei ungültigem Zahleninhalt eine eigene Exception `UngueltigeDatendatei` auslösen,
- die ursprüngliche `ValueError`-Exception als Ursache erhalten.

### Lösungsschema

Benötigt:

```text
eigene Exception:
UngueltigeDatendatei

with open(...)
→ Datei automatisch schließen

for zeile in datei
→ float(...)

ValueError abfangen
→ neue Exception mit raise ... from ...
```

`FileNotFoundError` muss nicht abgefangen werden, wenn sie unverändert weitergegeben werden soll.

<details>
<summary>Vollständige Lösung anzeigen</summary>

```python
class UngueltigeDatendatei(Exception):
    pass


def lese_werte(
    dateiname: str
) -> list[float]:
    werte: list[float] = []

    with open(
        dateiname,
        "r",
        encoding="utf-8"
    ) as datei:
        for zeilennummer, zeile in enumerate(
            datei,
            start=1
        ):
            try:
                wert = float(zeile.strip())

            except ValueError as e:
                raise UngueltigeDatendatei(
                    f"Ungültige Zahl in Zeile "
                    f"{zeilennummer}."
                ) from e

            werte.append(wert)

    return werte
```

Mögliche Behandlung beim Aufrufer:

```python
try:
    werte = lese_werte("werte.txt")
    print(werte)

except FileNotFoundError:
    print("Datei nicht gefunden.")

except UngueltigeDatendatei as e:
    print(f"Ungültige Datei: {e}")
```

</details>

# Zusammenfassung

## Exception

Eine Exception beschreibt eine außergewöhnliche Fehler- oder Ausnahmesituation.

```python
ValueError("Ungültiger Wert")
```

---

## `raise`

```python
raise ValueError(
    "Ungültiger Wert."
)
```

löst eine Exception aus und unterbricht den normalen Kontrollfluss.

---

## `try`

```text
try:
    ...
```

enthält Code, bei dem eine Exception behandelt werden soll.

---

## `except`

```text
except ValueError as e:
    ...
```

behandelt eine passende Exception.

---

## `else`

```text
else:
    ...
```

wird nur ausgeführt, wenn im `try` keine Exception aufgetreten ist.

---

## `finally`

```text
finally:
    ...
```

wird unabhängig vom Erfolg oder Fehler ausgeführt.

Typischer Zweck:

```text
Aufräumarbeiten
Ressourcen freigeben
```

---

## Exception weitergeben

```text
except ValueError:
    ...
    raise
```

gibt dieselbe Exception weiter.

---

## Exception Chaining

```python
raise NeueException(...) from e
```

erzeugt eine neue Exception und erhält die ursprüngliche Ursache.

---

## Eigene Exception

```python
class KontoFehler(Exception):
    pass
```

Eigene Exceptions können fachliche Fehler präzise ausdrücken.

---

## Ressourcenverwaltung

Für Dateien sollte normalerweise:

```python
with open(...) as datei:
    ...
```

verwendet werden.

Die Datei wird beim Verlassen des Blocks automatisch geschlossen.

## Merksätze

```text
raise
→ Diese Operation kann so nicht sinnvoll fortgesetzt werden.

try
→ Hier könnte eine Exception auftreten, die ich behandeln möchte.

except
→ So reagiere ich auf einen bestimmten Fehler.

else
→ Dieser Code läuft nur, wenn try erfolgreich war.

finally
→ Dieser Code läuft auf jeden Fall.

raise
im except
→ dieselbe Exception weitergeben.

raise NeueException(...) from e
→ Fehler übersetzen und Ursache erhalten.

with
→ Ressource sicher verwenden und automatisch aufräumen.
```

Der wichtigste Gedanke:

> Exceptions trennen das Erkennen eines Fehlers von der Entscheidung, wie auf diesen Fehler reagiert wird. Tiefer liegender Code kann einen ungültigen Zustand mit `raise` signalisieren, während eine passendere Ebene entscheidet, ob der Benutzer eine Meldung erhält, erneut gefragt wird, eine Operation zurückgesetzt wird oder die Exception weitergegeben werden soll.
